# Financial Report Regeneration Procedure

## Overview

CompactConnect emails settled-transaction (financial) reports to compact and jurisdiction operations staff on a
weekly and monthly cadence. These are generated by the `TransactionReporter` Lambda
(`ReportingStack`, handler [`generate_transaction_reports`](../../lambdas/python/purchases/handlers/transaction_reporting.py)),
which is triggered by EventBridge rules defined in [`reporting_stack.py`](../../stacks/reporting_stack.py).

For each run the Lambda:

1. Queries the transaction history table for the compact over the reporting window, keeping only transactions with a
   `settledSuccessfully` status.
2. Generates a **financial summary report** and a **transaction detail report** for the compact, plus a
   **transaction detail report** for every jurisdiction that is live for licensee registration in that compact.
3. Writes the reports to the transaction reports S3 bucket as zip files.
4. Invokes the email notification service to email each zip file as an attachment to the configured recipients
   (compact `COMPACT_SUMMARY_REPORT` contacts, and each jurisdiction's
   `jurisdictionSummaryReportNotificationEmails` contacts).

The Lambda is configured with `retry_attempts=0` — a failed run is **not** retried automatically. Failures raise the
`TransactionReporterFailure` alarm, which notifies the environment's alarm topic. When that happens, or when a report
is found to be missing or incorrect after the fact, a developer must re-run the report manually using this procedure.

### Schedules and default reporting windows

| Cycle | EventBridge schedule | Default window (inclusive display dates) |
| --- | --- | --- |
| `weekly` | Mondays at 04:00 UTC | The previous Saturday through Friday (7 days, ending at the most recent Saturday midnight UTC) |
| `monthly` | The 3rd of each month at 02:00 UTC | The 1st through the last day of the previous month |

Window math lives in [`report_window.py`](../../lambdas/python/purchases/report_window.py). All windows start and end
at midnight UTC; the query range is inclusive of the start and exclusive of the end, and the end date shown in the
report/email is the last full day in the window.

> Example: the weekly run on Monday 2025-04-07 covers 2025-03-29 (Saturday) through 2025-04-04 (Friday).
> The monthly run on 2025-04-03 covers 2025-03-01 through 2025-03-31.

## Prerequisites

Before beginning this procedure, ensure you have:

1. **AWS Console or CLI access** to the target environment (test, beta, or production) with permission to read
   CloudWatch logs, invoke Lambda functions, and read the transaction reports S3 bucket.
2. **The compact abbreviation** for the affected report (`aslp`, `octp`, or `coun` — see the `compacts` list in
   [`cdk.json`](../../cdk.json)).
3. **The reporting cycle and the exact window** the report should cover (see the table above).
4. **Awareness that re-running sends real emails.** A re-run emails the compact recipients *and* every live
   jurisdiction's recipients again — there is no way to limit the run to a single jurisdiction. Coordinate with the
   compact's operations contact before re-running in production. See
   [Re-sending a report without re-emailing everyone](#re-sending-a-report-without-re-emailing-everyone) if you only
   need to get a report to one recipient.

## Procedure

### Step 1: Determine what failed and why

1. Navigate to AWS Console → Lambda → Functions and find the transaction reporter for the environment. Its name
   contains `ReportingStack-TransactionReporter`.
2. Open the **Monitor** tab → **View CloudWatch logs**, or use the saved CloudWatch Logs Insights query definition
   named `ReportingStack/TransactionReporter`, and find the invocation for the failed run.
3. Identify the failure. The handler intentionally collects non-fatal errors and raises a single
   `CCInternalException` **after** the reports have been generated, stored, and emailed, so read the whole invocation
   before deciding what to do:

| Log message / error | Meaning | Action |
| --- | --- | --- |
| `Some providers were not found in the database` | A transaction referenced a provider ID that no longer resolves. Reports were still generated and sent, with `UNKNOWN` in the name columns. | Investigate the provider records. Re-running will not change the output until the underlying data is fixed. |
| `Unknown jurisdictions found in transactions` | A line item referenced a jurisdiction that is not configured/live for the compact. Reports were sent with an `UNKNOWN (xx)` row. | Check the compact's jurisdiction configuration. Re-run after the configuration is corrected if the report needs to show the jurisdiction properly. |
| `transaction line item id does not match any known pattern` | A line item ID did not match `*-compact-fee`, `credit-card-transaction-fee`, or `priv:*`. The fee was rolled into an `Unknown Line Item Fees` row. | Investigate the transaction record. Expected only in test environments with legacy data. |
| `Failed to send compact summary report email` / `Failed to send jurisdiction report email` | Report generation succeeded and the zip is in S3, but the email failed (most often no recipients configured for the compact/jurisdiction). | Fix the notification email configuration, then re-run per the steps below. |
| `The compact is not yet live - skipping reports` | The compact has no compact configuration or no live jurisdictions. This is a successful, no-op run. | No action needed unless the compact should be live. |
| Timeout / no log output | The invocation exceeded the 15-minute timeout, or never ran. | Re-run per the steps below and watch the duration. |

4. If the report ran successfully but is **missing transactions**, the problem is likely upstream in transaction
   collection, not reporting. The transaction history collection workflow
   ([`transaction_history.py`](../../lambdas/python/purchases/handlers/transaction_history.py)) is what pulls settled
   transactions from Authorize.net into DynamoDB. Regenerating a report will not create data that was never collected —
   resolve the collection gap first, then regenerate.

### Step 2: Determine the reporting window to regenerate

If you need to re-run a report, you must specify the window explicitly with the override fields.

Use the inclusive display dates for the period you want:

- Weekly: the Saturday through the following Friday, e.g. `2025-03-29` → `2025-04-04`.
- Monthly: the first through the last day of the month, e.g. `2025-03-01` → `2025-03-31`.

### Step 3: Build the event payload

The handler reads the following fields from the event:

| Field | Required | Type | Notes |
| --- | --- | --- | --- |
| `compact` | Yes | string | Lowercase compact abbreviation (`aslp`, `octp`, `coun`). |
| `reportingCycle` | Yes | string | Exactly `weekly` or `monthly`. Any other value raises a `ValueError`. |
| `reportStartOverride` | No | string | ISO date (`YYYY-MM-DD`). First day of the window, **inclusive**, at midnight UTC. |
| `reportEndOverride` | No | string | ISO date (`YYYY-MM-DD`). Last day of the window, **inclusive** — the handler adds a day internally to build the query range. |

Important behaviors of the overrides:

- **Both overrides must be supplied together.** If only one is present, both are ignored and the handler silently falls
  back to the default window for the cycle. Always double-check the window reported in the `Generating transaction
  reports` log line after invoking.
- **`reportingCycle` is still required when overriding dates.** With both overrides set it no longer affects the window;
  it only determines the `reporting-cycle/{weekly|monthly}` segment of the S3 key and the "Weekly"/"Monthly" wording in
  the email subject and body. Use the cycle that matches the report you are replacing so the regenerated file lands at
  the same S3 path.
- **The window is arbitrary.** Overrides are not restricted to whole weeks or months, so you can generate an ad hoc
  period if operations requests one — but a re-run intended to replace a scheduled report should use exactly the
  original window.

Re-run of a weekly report for a specific past week:

```json
{
  "compact": "aslp",
  "reportingCycle": "weekly",
  "reportStartOverride": "2025-03-29",
  "reportEndOverride": "2025-04-04"
}
```

Re-run of a monthly report for March 2025:

```json
{
  "compact": "aslp",
  "reportingCycle": "monthly",
  "reportStartOverride": "2025-03-01",
  "reportEndOverride": "2025-03-31"
}
```

### Step 4: Invoke the Lambda

**Via the AWS Console (preferred for production, since it makes the payload and result visible for review):**

1. Navigate to AWS Console → Lambda → the `ReportingStack-TransactionReporter` function for the environment.
2. Open the **Test** tab, select **Create new event**, paste the payload from Step 3, and give the event a name.
3. Click **Test** and wait for the invocation to complete (it can take several minutes for compacts with a large
   number of transactions).

Repeat the invocation once per compact if more than one compact is affected — each run handles a single compact.

### Step 5: Verify the run

1. **Check the response.** A successful run returns `{"message": "reports sent successfully"}`. If any error was
   collected during the run, the invocation ends with a `CCInternalException` listing the errors — note that reports
   may still have been generated and emailed before that exception was raised.
2. **Confirm the window in the logs.** Find the `Generating transaction reports` log entry and confirm the `window`
   field matches the intended dates (`YYYY-MM-DD--YYYY-MM-DD`). This is the check that catches a dropped or malformed
   override.
3. **Confirm the files in S3.** Navigate to the transaction reports bucket
   (`...PersistentStack-TransactionReportsBucket...`) and confirm the objects exist with a current timestamp:

   - Compact report:
     `compact/{compact}/reports/compact-transactions/reporting-cycle/{cycle}/{YYYY}/{MM}/{DD}/{compact}-{start}--{end}-report.zip`
   - Jurisdiction report:
     `compact/{compact}/reports/jurisdiction-transactions/jurisdiction/{jurisdiction}/reporting-cycle/{cycle}/{YYYY}/{MM}/{DD}/{jurisdiction}-{start}--{end}-report.zip`

   where `{YYYY}/{MM}/{DD}` is the **end** date of the window and `{start}--{end}` are the window's display dates.
4. **Confirm delivery.** Follow up with the compact operations contact that the emails arrived.

## Things to know before re-running

- **Re-runs overwrite the S3 objects for the same window.** The key is derived entirely from the compact, jurisdiction,
  cycle, and window dates, so a re-run of the same period writes to the same key. The bucket is versioned, so the prior
  version is retained and can be recovered if needed.
- **Re-runs email everyone again.** Every live jurisdiction in the compact gets its report re-sent along with the
  compact summary. There is no per-jurisdiction re-run option.
- **Emails are sent before the exception is raised.** Because the handler accumulates errors and raises at the end, a
  failed invocation does not mean emails were not delivered. Read the logs before re-running so recipients don't receive
  three copies of the same report.
- **Only `settledSuccessfully` transactions are included.** Transactions in a settlement-error state are deliberately
  excluded, because no money moved for them; Authorize.net reprocesses them in a later batch, and they will appear in
  the report for the window in which they eventually settle. A report that "looks short" may simply reflect a delayed
  settlement rather than a failure.

## Re-sending a report without re-emailing everyone

If the report generated correctly and only one recipient needs a copy (for example, a single jurisdiction reported that
the email never arrived), do **not** re-run the Lambda. Instead:

1. Download the relevant zip file from the transaction reports S3 bucket using the paths in Step 5.
2. Provide the file to the requesting party through the team's normal secure channel for operational data.

This avoids re-sending reports to every compact and jurisdiction contact.
